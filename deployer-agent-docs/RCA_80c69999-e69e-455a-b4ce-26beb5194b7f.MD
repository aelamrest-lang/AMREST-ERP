### 3. Production "entry" logs vs data.productionEntries (±120s)
Every `Production entry …` log in the retained window maps to a `productionEntries` record with `createdAt` within ±120s (checked 2026-11-02 → 11-05; e.g. log 06:59:58.049 ↔ entry 06:59:58.047). **No missing production entries in the verifiable window.** The "missing from Production page" perception is driven by the `date` field, not loss — see Q4.

### 4. Empty/invalid `date` and date distribution (BACKDATING)
- No empty/null `date` values found in sampled grns/productionEntries.
- **Future (invalid) dates (later corrected):** GRN-2026-340 set to `2026-11-29`, GRN-2026-333 set to `2026-11-29` (then edited back to 10-29).
- **Heavy backdating is pervasive.** GRNs created in the last 7 days carry `date` values spanning **2026-08-13 → 2026-11-04** (e.g. GRN-2026-329 created 10-30 dated 2026-10-06; GRN-2026-228 created 10-20 dated 2026-08-29; 227→08-21; 226→08-13; 315→10-06). Hundreds of `Edited GRN … Date 2026-11-02 → 2026-10-29/…` logs. ProductionEntries likewise: created 11-02 but dated 10-30/10-31; created 10-30 dated 10-26/10-27/10-29; one created 10-29 dated 10-20.
- **Consequence:** the GRN page and Production page display/sort/filter by the user-editable `date` field, while the Activity Log is ordered by creation time. A record created this week but back-dated weeks earlier is present in the DB and in the Activity Log, yet falls outside a "current / this-week" view on the page → looks "missing." This exactly matches the reported symptom and is a real contributor independent of concurrency.

### 5. Backend PUT /api/erp/state patterns (from runtime logs)
- Many concurrent users active (Bilal 79da8d36, u-purchase, u-production, u-admin, Parvez 3921f9bc, Sharafat 072f58e1). Interleaved `GET /api/erp/state` and `PUT /api/erp/state`, including clustered **`PUT /api/erp/state 200 OK ×3`** — multiple full-state saves within seconds → last-write-wins overwrite window.
- **Repeated `PUT /api/erp/state 401 Unauthorized`** — saves rejected on expired JWT. These writes never persist (and are not logged); the user may believe the save succeeded → a SEPARATE silent data-loss path.
- **`/health` upstream timeouts** at 06:50–07:06 (`upstream timed out … /health`). Backend runs **uvicorn --workers 1**; the erp_state document is multi-MB (it repeatedly exceeded the query size cap). A single worker serializing large full-document GET/PUT blocks, widening the race window and occasionally stalling requests.
- No HTTP 413/payload-too-large observed (PUTs return 200 or 401).

### 6. Backup / recoverability
- Only two collections exist: `files`, `erp_state`. **There is NO history / version-snapshot collection.** `erp_state` keeps a single monotonic `version` integer (7467) but no prior copies of the document.
- => **No in-DB source to recover clobbered records.** Recovery is only possible from MongoDB Atlas point-in-time / scheduled backups (external), if enabled on the cluster.

## Root cause
The whole ERP is one `erp_state` document saved by the frontend as a **full-document PUT with last-write-wins and no server-side merge**. With 6+ users saving within seconds (confirmed in backend logs), a client that holds a stale in-memory copy overwrites GRNs / Production entries other users added moments earlier. Because the 15s version-poll refreshes the activity feed while the client keeps its stale grns/productionEntries, the overwriting save can retain the newer **log** entry while dropping the corresponding **record** → "in Activity Log but missing from page." Proven by duplicate GRN numbers (184, 171, 135) and un-deleted sequence gaps.
Two amplifiers: (a) pervasive **date backdating / invalid future dates** hide existing records from date-filtered pages; (b) **401 failed saves** and a **single worker on a multi-MB doc** cause additional silent/lost writes.

## Suggested fixes (NOT applied)
- **Code (E1):** make writes concurrency-safe — optimistic concurrency on `version` (reject stale PUT with 409 → client refetch + merge), OR server-side merge of grns/productionEntries/logs, OR split into per-entity collections with atomic `$push`. Assign GRN numbers **server-side** to eliminate duplicates. Handle 401-on-save (silent refresh / block until saved). Only raise worker count after writes are safe.
- **Code (E1):** GRN & Production pages — reconcile `date` vs `createdAt`; show/flag records whose `date` is outside the active filter and reject implausible/future dates.
- **User:** confirm specific "missing" GRN/entry numbers so they can be matched; decide the backdating policy; and check whether MongoDB **Atlas backups (PITR)** are enabled for recovery of clobbered records.
